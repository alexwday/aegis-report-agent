Goal of G6: quarter-over-quarter automation. A saved report regenerates by itself when the next quarter's data is ready, with sensible rules for late, partial and corrected data, and clear status for the user. Start with CHG-017 to CHG-021.

## HUMAN DECISIONS ALREADY MADE (Q-012)

- Wait for COMPLETE required inputs by default. The owner may opt in to a PROVISIONAL output after a deadline; it is clearly labelled and later superseded by a complete output.
- Defaults, all configurable: timezone America/Toronto, quiet period before running, a 14-day correction window, no email delivery in this release.

## MUST

- 1. CHG-017 to CHG-021 with their acceptance runs (page 4) and NOTE-017. Give exact commands for every evaluation, including new flags such as --repeat. I will rerun the chat evaluation three times per case, the theme cases, and the TD slides and RTS cases with the real gateway through my private harness and judge them in R-007.
- 2. SCHEDULE EVALUATOR. A poller that, for each enabled schedule, determines the target fiscal quarter, probes readiness for every bank and source in the pinned version, applies the quiet period, and enqueues exactly one generation per (schedule, pinned version, target quarter, evidence state). Idempotent across duplicate polls and concurrent pollers; resumable after a crash; honours pause and archive; checks the owner with the OwnerStatusChecker before running. Use calendar dates only where a reliable mapping exists (Canadian banks); otherwise rely on physical readiness.
- 3. PUBLICATION RULES. A per-period 'current output' pointer. Complete output supersedes provisional. A later correction (changed source marker inside the 14-day window) triggers a new generation that supersedes the previous one atomically. An older generation finishing late must never replace a newer one (use the lease token and a generation counter). Retry transient failures with jitter and the existing attempt cap; show permanent failures clearly.
- 4. USER-VISIBLE STATUS. For each schedule period: state (waiting for data, ready to run, running, published, provisional, superseded, failed), which banks and sources are still missing, the next check time, what changed in the last correction, and a link to the output. Expose it through the API and the console, and add the wording to the reason catalog and the UI spec.
- 5. TESTS. Injected clock; duplicate and concurrent polls; pause while running; archive while waiting; mid-load marker change; a correction after publication; a provisional output superseded by a complete one; owner becomes inactive. Show the quarter roll-forward in the demo.
- 6. DRY-RUN EVALUATOR. `scripts/eval_schedule.py` takes a report spec file (or a template and bank list), a target quarter and a read-only DSN, probes readiness exactly as the poller would, and prints per-bank and per-source state without writing anything. I will run it against the real dev sources and report in R-007 (for example the Big 6 earnings brief for FY2026 Q3 and a future quarter).
